# Testing Philosophy（テスト方針）

並列開発におけるテスト戦略の詳細ガイド。

## 原則: 本番に近い状態でテストする

モックや擬似データを多用するのではなく、実際の環境に近い状態でテストを行うことで、本番デプロイ後の問題を未然に防ぐ。

### なぜ本番同等テストか

- モックで通っても本番で動かないケースを防ぐ
- 外部API の仕様変更・レート制限・認証エラーを早期検知
- DB スキーマ・データ整合性の問題を実データで検証
- 複数サービス間の連携を実際に確認

## 本番同等テストの対象

| 対象 | 方針 |
|------|------|
| 外部 API | 実際の API キーを使用（テスト用アカウント推奨） |
| データベース | 実際の DB に接続（開発/ステージング環境） |
| 認証・認可 | 実際のトークン・セッションを使用 |
| ファイルストレージ | 実際の S3/GCS 等に接続 |
| メール・通知 | テスト用アドレスに実送信、または sandbox モード |

## 環境設定

worktree ごとに `.env` をコピーし、本番同等のシークレットを設定:

```bash
# worktree 作成時（SKILL.md の環境セットアップ参照）
cp .env worktree/$BRANCH/.env

# .env には本番同等の接続情報を含める
# - DATABASE_URL（開発/ステージング DB）
# - API キー（外部サービス）
# - 認証情報
```

**注意**: テスト専用の API キー・DB を用意し、本番データを破壊しないよう注意する。

## テスト実行タイミング

マージ担当が統合ブランチにマージする前に、本番同等環境でテストを実行:

```
1. 作業用 claude が .done 作成
2. マージ担当がコミット
3. 統合ブランチの最新をマージ
4. ★本番同等テスト実行★  ← ここで外部API・DB連携を検証
5. テスト成功 → プッシュ＆マージ
6. テスト失敗 → 修正依頼
```

## テストコマンドの例

```bash
# 本番同等テスト（外部API・DB接続あり）
DATABASE_URL=$DATABASE_URL \
API_KEY=$API_KEY \
uv run pytest tests/ -v

# または
pnpm test:integration
```

## E2E 目視チェック（マージ担当）

マージ担当は dev-browser スキルを使い、ブラウザで実際の画面を確認する:

1. **開発サーバー起動**: worktree でサーバーを起動
2. **ブラウザで画面を開く**: dev-browser スキルで URL にアクセス
3. **スクリーンショット取得**: 主要画面のスクリーンショットを撮影
4. **LLM による目視確認**: スクリーンショットを見て UI の状態を確認

```
# dev-browser スキルを使用
/dev-browser

# 操作例
- http://localhost:{port} にアクセス
- 主要画面に遷移
- スクリーンショットを撮影
- UIの表示、レイアウト、エラー表示がないかを確認
```

### 確認ポイント

- レイアウト崩れがないか
- エラーメッセージが表示されていないか
- 期待する要素が表示されているか
- コンソールエラーがないか

### 目視チェックが必要なタスク

- フロントエンド（UI）を含むタスク
- 画面遷移・ナビゲーションに影響するタスク
- レイアウト・スタイリングを変更するタスク

### 目視チェックが不要なタスク

- バックエンドAPIのみのタスク
- バッチ処理・CLIツールのタスク

## テストデータの扱い

| 種類 | 方針 |
|------|------|
| 読み取りテスト | 既存の開発データを使用 |
| 書き込みテスト | テスト後にクリーンアップ、またはトランザクションロールバック |
| 破壊的テスト | 専用のテストテナント/名前空間を使用 |
